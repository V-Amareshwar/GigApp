## AUTHENTICATION FLOW (EXACT)

```
1. User opens app
2. Firebase Phone OTP sent to mobile number
3. User enters OTP in app
4. App sends {phone, firebase_token} to backend
5. Backend verifies firebase_token with Firebase Admin SDK
6. Backend checks if user exists in PostgreSQL
   → If new user: create user record → generate JWT
   → If existing user: fetch user → generate JWT
7. Backend returns {access_token, refresh_token, user}
8. App stores tokens in SecureStore (Expo)
9. All future API calls use JWT Authorization header
10. JWT expires in 15 minutes → auto-refresh using refresh_token
```

## ALGORITHM ARCHITECTURE

### 1. Weighted Job Matching Algorithm

```
Step 1: Filter by city (eliminates 95% of records instantly)
Step 2: Filter by category (further narrows results)
Step 3: Calculate matching score for remaining jobs

Score Formula:
matching_score = (
  (skill_match_score    × 0.40) +
  (location_score       × 0.30) +
  (salary_match_score   × 0.20) +
  (availability_score   × 0.10)
)

Range: 0.00 to 1.00
Higher score = shown first in recommendations
```

### 2. Haversine Distance Algorithm

```
Step 1: Filter by city first (SQL WHERE city = user_city)
Step 2: Apply bounding box (approximate square before circle)
Step 3: Calculate exact Haversine distance for remaining records
Step 4: Return jobs sorted by distance ASC

Formula:
a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlng/2)
c = 2·atan2(√a, √(1−a))
d = R·c   (R = 6371 km)
```

### 3. Trust & Rating Algorithm

```
trust_score = (
  (avg_rating          × 0.35) +
  (completed_jobs_norm × 0.25) +
  (attendance_score    × 0.20) +
  (verification_bonus  × 0.10) +
  (report_penalty      × -0.10)
)

Range: 0.0 to 5.0
Update trigger: ONLY when review added / report submitted / job completed
NOT recalculated on every request
```

### 4. PostgreSQL Full Text Search

```
Search vector built from: title + description + category + city
Index type: GIN (Generalized Inverted Index)
Ranking: ts_rank() for relevance scoring
Pipeline: FTS → filter by city → filter by status=active → sort by ts_rank
```

### 5. Rule-Based Scam Detection

```
Scam score = sum of triggered rules

Rules:
│ salary > 3x market average for category  → +0.40 score
│ description contains "registration fee"   → +0.80 score
│ description contains "deposit required"   → +0.80 score
│ description contains links (http/www)     → +0.20 score
│ description contains MLM keywords         → +0.90 score
│ employer asking to contact outside app    → +0.30 score
│ new account (<24hrs) posting >2 jobs      → +0.30 score
│ same description posted >3 times          → +0.50 score

If scam_score >= 0.70 → job held for review
If scam_score >= 0.90 → job auto-rejected
If scam_score <  0.70 → job posted normally
```

## NOTIFICATION ARCHITECTURE

```
Triggers:
→ New nearby job matching worker skills     → Push to worker
→ Application received                      → Push to employer
→ Application accepted                      → Push to worker
→ Application rejected                      → Push to worker
→ New chat message                          → Push to recipient
→ Review reminder (24hr after completion)   → Push to both
→ Job about to expire (24hr warning)        → Push to employer

Channel: Firebase Cloud Messaging (FCM)
Storage: notifications table in PostgreSQL
Delivery: Fire-and-forget (non-blocking API responses)
```

## SECURITY ARCHITECTURE

```
1. All API routes protected by JWT middleware (except auth routes)
2. Role-based access control (seeker routes vs provider routes)
3. OTP rate limiting: max 5 OTP requests per phone per 10 minutes
4. API rate limiting: 100 requests per minute per IP
5. JWT: 15-minute access token + 30-day refresh token
6. Refresh tokens stored in DB (allows revocation on logout)
7. All passwords/secrets in environment variables
8. Supabase Row Level Security (RLS) enabled
9. Input validation on all API endpoints
10. SQL injection prevention via parameterized queries
```
